# 签前评测报告

每个数字都能用脚本复现，出处写在表格下面。这份是初稿，第 1 节是 T08 法条检索，第 2 节是 T09 审查流程；注入测试（T15）、四组对照（T17）完成后各补一节。

## 1. 法条检索（T08）

### 1.1 评测集

- **测试集** `eval/retrieval/test.json`：30 条。前 15 条照合同条款的写法写（"乙方因病连续请假超过 30 天的，本合同自动终止"），后 15 条是学生口语提问（"公司换了老板，以前签的合同还算数吗"）。话题以规则引擎覆盖不到的为主：加班工资、年休假、扣工资、未签书面合同、经济补偿、违法解除、仲裁时效、劳务派遣等。每条标了能作为依据的条文 ID，平均 3.0 个，第一个是最直接的那条（下称主依据）。主依据分布：劳动合同法 19 条，劳动法 3 条，工资支付暂行规定、劳动争议调解仲裁法各 2 条，实施条例、解释（一）、社会保险法、年休假条例各 1 条。
- 测试集在检索代码之前提交（提交 `8bc94c6`），之后没有改过题目和答案。
- **开发集** `eval/retrieval/dev.json`：T03 抽查用过的 10 条。提示词只在开发集上调过（rewrite-v1 → v2、rerank-v1 → v2，原因写在 `src/prompts/retrieval.ts` 开头）。提示词里的示例只用开发集的话题（押金、扣证件）。
- **法规库**：11 部法规 524 条，加 6 个典型案例切成的 18 段，共 542 个检索单元。

### 1.2 六种配置

| 配置      | 做法                                                                        |
| --------- | --------------------------------------------------------------------------- |
| text      | 原句，只走全文检索（二字切分 + BM25）                                       |
| vector    | 原句，只走向量检索（bge-small-zh-v1.5）                                     |
| hybrid    | 原句，全文和向量各取前 20，RRF 合并                                         |
| hybrid+rr | hybrid 的前 20 交给模型重排                                                 |
| rewrite   | 模型把原句改写成 2~3 个法条用语的查询，原句和改写各走两路，所有名单一起 RRF |
| full      | rewrite 的前 20 交给模型重排（线上用这个）                                  |

改写和重排用 Deepseek-v4-flash（微信 API 平台），不开思考模式。重排只能输出候选里的条文 ID：结构化输出的 schema 用候选 ID 做枚举，模型写不出库里没有的 ID。

### 1.3 结果

30 条 × 2 轮，共 60 次。前 5 命中：gold 里任意一条进了前 5。

| 配置      | 前 5 命中    | 主依据进前 5 | MRR   | 条款原文 | 口语提问 |
| --------- | ------------ | ------------ | ----- | -------- | -------- |
| text      | 28/60（47%） | 26/60（43%） | 0.336 | 60%      | 33%      |
| vector    | 40/60（67%） | 28/60（47%） | 0.473 | 73%      | 60%      |
| hybrid    | 38/60（63%） | 30/60（50%） | 0.436 | 80%      | 47%      |
| hybrid+rr | 53/60（88%） | 42/60（70%） | 0.829 | 93%      | 83%      |
| rewrite   | 55/60（92%） | 44/60（73%） | 0.658 | 87%      | 97%      |
| full      | 58/60（97%） | 52/60（87%） | 0.939 | 93%      | 100%     |

出处：`npm run eval:retrieval -- --rounds 2`，结果文件 `eval/results/2026-10-30-retrieval-test.json`。text、vector、hybrid 不调模型，两轮结果相同。

- 样本小，数字的误差范围要一起看：full 的 58/60 按二项分布算 95% 区间约 89%~99%，主依据 52/60 约 76%~93%。两轮用的是同一批查询，不是 60 个独立样本，实际误差比这更大。按查询数：30 条里 28 条两轮都命中，2 条（t04、t09）各命中一轮。
- 送去重排的前 20 条里有 gold 的：原句 54/60，改写后 60/60。改写主要是把正确条文带进候选，重排再把它排到前面。
- 口语提问对全文检索最难（33%）：问句里的"换了老板""干了八个月就被辞退"在法条里没有对应的字。full 在口语提问上 30 次全部命中。
- 两轮分开看，full 分别是 28/30 和 30/30。
- 开发集上调提示词期间跑了三次，full 是 9/10、9/10、8/10。8/10 那次有 3 条的模型调用全部失败，退回了原句检索。

### 1.5 耗时

| 步骤                     | 中位数  | p90     | 最慢    |
| ------------------------ | ------- | ------- | ------- |
| 改写                     | 4.0 秒  | 10.2 秒 | 18.2 秒 |
| 检索（本机，3~4 个查询） | 0.20 秒 | 1.09 秒 | 1.70 秒 |
| 重排                     | 3.9 秒  | 11.7 秒 | 28.0 秒 |
| 合计                     | 9.4 秒  | 21.8 秒 | 31.7 秒 |

- 两轮差别很大：第 1 轮合计中位数 12.6 秒，第 2 轮 5.5 秒，代码和数据都一样，差在平台响应。
- 检索在本机（i7-8750H）测，不加 `--liftoff-only`。服务器上 MCP 服务加这个参数，T03 实测单个查询编码约 53ms，4 个查询约 0.2 秒加全文检索，T12 部署后实测补上。
- 重排的输入：20 条候选每条截前 300 字，提示词中位数 3518 字、最长 5210 字。

### 1.6 平台的挂起请求和对冲

评测期间平台有请求长时间不返回。测试集两轮共发出 221 次请求，9 次到时限（改写 15 秒、重排 20 秒）没有返回，占 4.1%（95% 区间 2.2%~7.6%）；另有 2 次是平台连续报错、重试用尽。只回一个字的小请求单独试过两次共 11 个，2 个到 30 秒、60 秒没回，样本太小，只说明小请求也会挂住，不能当比例用。所以接入层加了两项（`src/lib/ai/core.ts`）：

- **时限**（`timeoutMs`）：每份请求的上限，到了算失败，换下一个角色。改写 15 秒，重排 20 秒。
- **对冲**（`hedgeMs`）：第一份请求过了这个时间还没回，就向下一个角色再发一份，先成功的算数，另一份取消。改写 5 秒，重排 8 秒。

测试集两轮里，改写和重排一共 180 次调用，有 34 次（19%，95% 区间 14%~25%）过了对冲点还没回，于是多发了一份，实际请求 221 次，比 180 次多 23%。取消的那份也按 1 次请求计，平台按发出的请求计数。超时 9 次、重试用尽 2 次，都由另一份请求顶上或降级处理；60 次里有 4 次出现降级，都是重排失败，退回 RRF 顺序。

### 1.7 结论

- 线上用 full。改写对口语提问作用最大，重排对条款原文作用最大，两步都留。
- 每次检索要 2 次模型调用，合计中位数 9.4 秒。T09 里规则能判的条款不走检索。规则覆盖不到的条款走改写和检索，不单独重排，前 8 条候选交给判断步骤挑依据，每条省一次调用。T09 试过让抽取步骤顺带写查询，录用通知样例里它只把原句抄了一遍，候选全偏到试用期条文上，所以没用。
- t09 这类"单方变更工作地点"的条款，T09 的规则工具 `check_unilateral_terms`（R14）直接覆盖，不依赖检索。

## 2. 审查流程（T09）

### 2.1 做法

`src/lib/review/run.ts`：抽取 → 计划 → 执行 → 自检 → 报告，每一步推事件。和项目方案第 4 节的差别：

- 计划由程序按抽取出的字段生成（`plan.ts`），不单独调模型。字段和规则工具的参数一一对应，有值就调对应的工具。
- 规则工具由程序直接调，一处约定调一次，结论直接挂在那段原文上。模型只判断规则覆盖不到的条款，依据只能从这一条自己的检索结果里选。
- 抽取完成后三路并行：规则工具、模型核对抽取字段、规则覆盖不到的条款检索加判断。
- 程序检查四项：抽取字段的出处在不在合同里（找不到的字段不拿去算）；同一段话被归进两类时按规则字段算；每条批注的出处和依据条文 ID 是否有效；报告里的数字是否出现在前面步骤的材料里。

### 2.2 思考模式

T05 定的是自检开 high、报告开 medium。整套流程跑起来后实测：

| 步骤和强度  | 结果                                                                  |
| ----------- | --------------------------------------------------------------------- |
| 自检 high   | 录用通知样例一次核对，两份请求 80 秒都没返回，整次检查撞上 120 秒时限 |
| 报告 medium | 3 条批注写了 48 秒，输出 6089 tokens                                  |
| 抽取 low    | 四份样例全部 60 秒没返回（两个角色各试一次）                          |
| 都不开      | 见下表，一份合同 19~81 秒                                             |

所以默认都不开（`src/lib/ai/config.ts`），环境变量可以单独打开。不开思考时抽取会归错类、编出可为空的字段，靠 2.1 的程序检查兜底：开发过程中先后发现编出的"住房换服务期"、quote 为空的竞业限制、被当成解除条件的辞职条款，都由程序检查拦下。

没对上的主要几类：

- 录用通知"毕业证、学位证原件交人事部统一保管"两轮都被归进了"其他条款"，没走规则 R10，由模型判断给出"可能违法"，依据劳动合同法第九条。用户能看到提醒，等级比规则低一级。

少对上的几条都能在抽取结果里找到原因：

### 2.4 还没做的

- 3 页合同从拍照到报告的完整耗时：四份样例都在 1~2 页，识别（T06 实测两页 36.7 秒，含第一次下载识别组件）和审查还没在界面上串起来，T10 做检查页时一起测。
